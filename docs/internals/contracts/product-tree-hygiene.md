# Product tree hygiene

**The rule: nothing development-related lives in a checkout.**

The product tree carries the product — source, tests, named fixtures, config,
and the in-repo engineering docs you are reading. It does not carry what a
developer or an agent *generates while working on the product*.

Enforced on every pull request by
[`scripts/ci/product-tree-hygiene.mjs`](../../../scripts/ci/product-tree-hygiene.mjs),
wired as the **Product Tree Hygiene Gate** step of the pure-node `gates` job in
[`.github/workflows/gates.yml`](../../../.github/workflows/gates.yml). The gate
asserts against the **tracked** tree (`git ls-files`), so a gitignored file in
your working copy is never a finding — only what a commit would carry.

It **blocks merges** once the branch protection lists `gates` as a required
status check. `gates` is the whole consolidated micro-gate runner, not this gate
alone: the hygiene guard is one step inside that job, so a red step surfaces as
a red `gates` check. The requirement is declared in
[`.github/branch-protections.json`](../../../.github/branch-protections.json),
which is the target policy, not the live one — it has to be re-applied to
GitHub with the `gh api -X PUT` command in that file's header before the
requirement actually binds.

## The forbidden set

Two anchoring classes, and the difference is load-bearing.

**Any depth** — never a legitimate product path at any level, so
`packages/x/evidence/y.png` fails exactly as `evidence/y.png` does:

| Path | Why it is not product |
|------|----------------------|
| `node_modules/` | An install. The toolchain rebuilds it from the lockfile. |
| `.next/` | Build output. |
| `.pytest_cache/`, `__pycache__/` | Test/interpreter caches. |
| `.claude/` | Agent configuration and session scratch — per-machine, per-operator. |
| `.planning/` | Planning notes. Planning lives in the tracker. |
| `evidence/`, `pr-evidence/` | Proofs and screenshots. These belong on the PR. |

**Root only** — anchored at the repository root, because the same name is real
product elsewhere in the tree (nested, or at a designated home):

| Path | Why root-anchored |
|------|-------------------|
| `data/` | Local runtime data. Nested, `data` is a real route segment — this repo tracks `src/app/agents/[vendor]/[packageName]/[instanceId]/data/page.tsx`. |
| `dev/` | Dev-app clones synced by `cinatra setup`; the companion repos are the source of truth. |
| `extensions/` | The root clone target for `@cinatra-ai/*`. Nested, `packages/extensions/` is a tracked workspace package. |
| `test-results/` | Per-run Playwright output. |
| `next-env.d.ts` | Regenerated by Next.js on every build; never authored. |
| `.env.local`, `.env.*.local` | Machine-local environment — and a credential risk. |
| `vitest.integration-*.config.{ts,mts,js,mjs}` | Per-slice integration tiers, one config per issue number, accreted at the root until the root listing read as a worklog. These are real product; they live at `vitest/integration/<NNNN>.config.ts`, which the root-anchored rule deliberately does not match. |

This gate landed **last**, after the branch that moved `evidence/` out of the
tree and the one that consolidated the 12 root `vitest.integration-*.config.ts`
tiers into `vitest/integration/`, so that it was green on the tree it first
guarded.

## Why the rule exists

A checkout is a working copy of the product, not a workspace for the work. When
development artifacts land in it they are wrong in three separate ways at once:

- **Proofs go stale in place.** A screenshot committed next to the code it
  depicts keeps asserting something that stopped being true at the next commit,
  and nothing tells the reader which one it is. Proofs are recorded **on the
  PR**, where they are pinned to a commit SHA and read in the context that
  produced them.
- **Working notes are not shared truth.** Planning notes and agent scratch
  describe one operator's in-flight intent. Merged into the tree they read as
  the project's position. Planning belongs in the tracker.
- **Generated files are not inputs.** Installs, build output, and caches are
  reproducible by definition; tracked, they only rot, conflict, and inflate
  every clone.

The distinction that matters for tests: **a real test input is a named fixture
under `tests/**`**. A fixture is authored, named for what it represents, and
part of the product. A capture of a run is output — it goes to the run's
artifacts, never into the tree.

A pre-commit hook enforces this on one machine. This gate enforces it for the
org, which is why a stray directory cannot re-enter the tree by way of a rebase,
a `git add -A`, or an agent working from a different profile.

## There is no allowlist

Deliberately. An allowlist is how a rule like this dies: the first exception is
argued once, and from then on the list is the policy.

If a path is genuinely product, it does not match these names. If it matches
these names, it is not product. Where a legitimate product path collided with a
forbidden name — the `data` route segment, the `packages/extensions/` workspace
package — the fix was to **anchor the rule at the root**, in the open, in the
gate's own rule set. A rule that needs an exception is a rule that is wrong, and
it gets fixed there.

## Running it

```sh
node scripts/ci/product-tree-hygiene.mjs            # tracked tree; exit 1 on any hit
node scripts/ci/product-tree-hygiene.mjs --json     # {hits:[{path,rule}]}
git ls-files | node scripts/ci/product-tree-hygiene.mjs --stdin
node --test scripts/ci/__tests__/product-tree-hygiene.test.mjs
```

Each hit prints as `<rule>\t<path>`, followed by a per-rule summary count.

To clear a finding: remove the path from the tree
(`git rm -r --cached <path>`) and add it to `.gitignore`.
