cinatra#2274 AC5 — IDEMPOTENT under re-registration

AC5 asks that a second registration pass does not regress a head back to a bundle
of one and does not churn a fresh revision per boot. Three passes reached the
registration writer against ONE database in this lane:

  pass 1  dev boot        — src/lib/extensions-dev-watcher.ts skill-walk scan
  pass 2  next start boot — the production server's own boot registration
  pass 3  chat turn       — packages/skills/src/extension-skill-resolver.ts via
                            ensureAssistantSkillsRegistered on the native-MCP turn

MEASURED row counts:
  after pass 1 : revisions=28 files=52 heads=28 skills=28
  after pass 3 : revisions=28 files=52 heads=28 skills=28

AGGREGATE COUNTS ALONE WOULD NOT PROVE THIS — a replacement preserves a count.
(codex raised exactly that.) They are load-bearing HERE because of three
structural facts, each read from committed source, not assumed:

  (a) skill_revisions is APPEND-ONLY at the database level.
      migrations/core/core__0029_skill-lifecycle.mjs:67
        CREATE TRIGGER trg_skill_revisions_append_only
        BEFORE UPDATE OR DELETE ON skill_revisions FOR EACH ROW ...
      So 28 rows after pass 3, having been 28 after pass 1, are the SAME 28 rows:
      no row could be deleted, so no row could be replaced, and the count could
      only ever go UP. It did not. ZERO revisions were minted by passes 2 and 3.

  (b) skill_revision_files is APPEND-ONLY the same way
      (trg_skill_revision_files_append_only, BEFORE DELETE OR UPDATE). 52 rows
      after pass 1 and 52 after pass 3 ⇒ the same 52 manifest rows, and ZERO
      manifest rows were written by passes 2 and 3.
      52 = 22 single-file bundles + (8+6+5+4+4+3) for the six multi-file bundles.

  (c) a DERIVED (capture-installed) head writes its manifest rows under a
      'bundle:<digest>' revision id — which would ADD rows to that same
      append-only table. None were added, so no derived manifest was ever
      written at any point, not merely at the end.

Head state at the end (results/AC3-bundle-authority-set-equality.json):
  head rows                    : 28
  DISTINCT head revision ids   : 28   (one per skill)
  derived ('bundle:') heads    : 0
  heads with an empty revision : 0

With 28 append-only revisions across 28 skills, and every skill carrying a
non-derived head whose manifest is non-empty, each skill has EXACTLY ONE
candidate revision its head can point at. There is nothing else for a head to
have moved to and back from.

WHAT IS STILL NOT MEASURED, stated plainly: skill_bundle_heads is a MUTABLE
pointer table with no append-only trigger, and this lane did not snapshot
(skill_id, revision_id) row-by-row after each pass. The argument above closes
the gap by elimination — no alternative revision and no derived manifest ever
existed — rather than by a per-row before/after diff.
