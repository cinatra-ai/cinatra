Verdict: do not accept this package as closing all three ACs. The execution itself is credible, but AC1’s persisted-turn requirement and AC2’s real chat-surface requirement are not met.

1. Unsupported or false WALK claims

- “Provider and resolved model id are recorded in `response.json`” is false. The response files contain `model` but no `provider`; see [ac1-openai-native/response.json](<worktree>/evidence/1705-ac123/raw/ac1-openai-native/response.json:1) and [ac1-anthropic/response.json](<worktree>/evidence/1705-ac123/raw/ac1-anthropic/response.json:1). Provider identity is inferable from directories/wire format and stated in WALK, but not recorded where WALK claims it is.

- “The raw persisted turn is retained, not a projection” is false. The driver serializes the in-memory normalized `generate()` return itself ([driver](<worktree>/evidence/1705-ac123/drivers/live-provider.walk.test.ts:265)). Both adapters manufacture `rawBody` as `JSON.stringify({text: finalText})`, explicitly a projection: [OpenAI adapter](<worktree>/extensions/cinatra-ai/openai-connector/src/adapter/openai-adapter.ts:679), [Anthropic adapter](<worktree>/extensions/cinatra-ai/anthropic-connector/src/adapter/anthropic-adapter.ts:892). The wire files are useful raw provider captures, but they are log captures, not a persisted Cinatra chat/agent turn. OpenAI also used `store:false` ([wire response](<worktree>/evidence/1705-ac123/raw/ac1-openai-native/wire-2026-08-01T19-24-20-560Z__ac123-ac1-openai-native-step-1__response.json:49)).

- “No credential value appears anywhere in this directory” is false. The runner contains a PostgreSQL password and a default broker-signing secret: [run.sh](<worktree>/evidence/1705-ac123/drivers/run.sh:34) and [run.sh](<worktree>/evidence/1705-ac123/drivers/run.sh:41).

- The passphrase does not “exist nowhere else.” It is literal test source at [driver](<worktree>/evidence/1705-ac123/drivers/live-provider.walk.test.ts:463) and in WALK itself at [WALK.md](<worktree>/evidence/1705-ac123/WALK.md:246). The wire call still proves the model read the file, but that prose claim is plainly wrong.

- “All six arms in a single invocation” is plausible from timestamps, but not established: there is no test-run transcript, manifest, or hashes binding the artifacts to one invocation. The driver actively deletes prior captures before rewriting them ([driver](<worktree>/evidence/1705-ac123/drivers/live-provider.walk.test.ts:223)).

3. Deviations are not completely disclosed

The “three deviations, all named” statement is inaccurate.

- The harness replaces `server-only` and the entire auth module with test stubs ([walk.config.ts](<worktree>/evidence/1705-ac123/drivers/walk.config.ts:16), [walk.config.ts](<worktree>/evidence/1705-ac123/drivers/walk.config.ts:29)). Those are not among WALK’s three.

- It runs with `CINATRA_REQUIRE_ACTOR_CONTEXT=false` and `NODE_ENV=test` ([run.sh](<worktree>/evidence/1705-ac123/drivers/run.sh:43)); production explicitly never permits that actor-context bypass ([LLM entry point](<worktree>/packages/llm/src/index.ts:446)). The flag is probably inert here because actor context is explicitly supplied, but it remains an undisclosed environmental deviation.

- AC3 does not attach a catalog-resolved skill through production attachment composition. It constructs a `SkillSummary` manually, writes directly under `data/skills`, and passes the resulting tool directly to `generate()` ([driver](<worktree>/evidence/1705-ac123/drivers/live-provider.walk.test.ts:478), [driver](<worktree>/evidence/1705-ac123/drivers/live-provider.walk.test.ts:571)). The direct-`generate()` deviation gestures at this, but calling it a normally “attached” skill overstates what ran.

- The skills stub is not equivalent to production containment. It performs only lexical containment ([stub](<worktree>/evidence/1705-ac123/drivers/skills-barrel-stub.ts:39)); production additionally applies realpath/symlink containment and accepts three configured roots ([skills-store.ts](<worktree>/packages/skills/src/skills-store.ts:1594)). WALK’s description of “the real function’s fail-closed shape” is incomplete.

4. Per-command rows and cumulative egress

The raw evidence substantively shows four executions per AC1/AC2 arm: four ordered provider commands and audit rows with unique `commandId`s and `seq=0..3`. For example, the native call has the four commands at [wire response](<worktree>/evidence/1705-ac123/raw/ac1-openai-native/wire-2026-08-01T19-24-20-560Z__ac123-ac1-openai-native-step-1__response.json:25), while its audit rows have sequences 0–3 at [audit rows](<worktree>/evidence/1705-ac123/raw/ac1-openai-native/audit-rows.json:13). Production executes the array sequentially ([executor.ts](<worktree>/packages/execution-plane/src/executor.ts:229)).

But “matching” is only ordinal/inferred. Persisted rows omit command text and the captured query omits the audit `resource_id`/job ID; provider captures do not contain audit `commandId`s. There is no direct join from a particular wire command to a particular row. The driver also fails to assert the sequence/cardinality.

The cumulative-egress reading is correct. The rows are `0, 0, 79354, 79354` ([audit rows](<worktree>/evidence/1705-ac123/raw/ac1-openai-native/audit-rows.json:23)); gateway statistics accumulate by job token and return a snapshot total ([egress-gateway.cjs](<worktree>/packages/execution-plane/runtime/egress-gateway.cjs:360)), which the worker fetches after each command ([worker.ts](<worktree>/packages/execution-plane/src/worker.ts:185)). The `79354` delta occurs on `seq=2`; `seq=3` adds zero. WALK is right on this point.

5. AC3 zero-row explanation

Yes, that explanation matches production code.

For an incompatible model, translation emits `skill_file_read` instead of native shell ([openai-adapter.ts](<worktree>/extensions/cinatra-ai/openai-connector/src/adapter/openai-adapter.ts:229)). Calls are routed to `executeSkillFileReadCall`, which invokes the local skill shell tool directly, not `sandbox_execute` ([openai-adapter.ts](<worktree>/extensions/cinatra-ai/openai-connector/src/adapter/openai-adapter.ts:367)). `createLocalSkillShellTool.execute` reads locally ([skills.ts](<worktree>/packages/llm/src/tools/skills.ts:183)). Therefore zero sandbox/voucher rows ([raw audit](<worktree>/evidence/1705-ac123/raw/ac3-openai-skill-degrade/audit-rows.json:1)) is the expected production architecture—subject to the lane using its weaker reader stub.
