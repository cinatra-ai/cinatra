NOT MERGE-SAFE.

Q1. The intended widening is limited to host-authored bytes. The DIRECT arm requires a registered artifact type, an eligible accepted binding, a live blob representation, and the exact `(org, artifact, representation)` witness ([object-content-snapshot.ts:889](<lane-worktree>/src/lib/artifacts/object-content-snapshot.ts:889)). A typed-DATA row without a host-written representation/witness cannot enter it. Nor does this expose another claimant’s `objects.data` view: the admitted bytes are not a claimant-keyed serialization. The stale-binding window in Q3 is the exception to the claimed “current claimant” guarantee.

Q2. Omitting `snapshotPolicy` is correct for this arm. `snapshotPolicy` governs whether mutable `objects.data` may be serialized; DIRECT serializes nothing and requires `pinnable=true` plus writer provenance. Requiring `snapshotPolicy='content'` would wrongly exclude genuine immutable file artifacts such as CMS snapshots, whose registered policy is deliberately `snapshotPolicy:'none'` ([register-all-object-types.ts:241](<lane-worktree>/src/lib/register-all-object-types.ts:241)). This does not widen access to row data.

Q3. It is not an equivalent fail-closed current-winner guard. `sa_one_active_binding_idx` guarantees only “at most one non-archived binding” ([semantic-assertion-schema.ts:118](<lane-worktree>/src/lib/semantic-assertion-schema.ts:118)); it does not prove that binding is the live claim winner. Winner changes update `artifact_type_claims` and enqueue reconciliation ([artifact-claim-store.ts:236](<lane-worktree>/src/lib/objects/artifact-claim-store.ts:236)); bindings are archived/replaced later by the asynchronous drain ([binding-reconcile-sweep.ts:323](<lane-worktree>/src/lib/objects/binding-reconcile-sweep.ts:323)). During that window, the old binding remains the sole eligible binding and passes `b.id = sa.id`, `eligibility='eligible'`, and `pinnable=true` ([context-selection-finalize.ts:172](<lane-worktree>/src/lib/artifacts/context-selection-finalize.ts:172)). Validate the exact binding against the live winner—including claim ID, generation, extension, scope precedence, and current object type—in every DIRECT gate.

Q4. Under one MVCC snapshot the predicates are exclusive, but these statements do not share one snapshot. `runPostgresQueriesSync` begins a transaction only when `transaction:true`; otherwise it executes each query separately ([postgres-sync.ts:43](<lane-worktree>/src/lib/postgres-sync.ts:43)). The call at `queries: [directQuery, candidateQuery]` omits that flag ([object-content-snapshot.ts:957](<lane-worktree>/src/lib/artifacts/object-content-snapshot.ts:957)).

- `false → true` between statements can make the row match neither.
- `true → false`, for example GC removing the joined resource, can make it appear in both results.
- Both arms independently apply `LIMIT 500`, so the advertised global cap and global narrowest-first truncation are also broken; up to 1,000 rows can be returned.

Use one SQL statement with a shared candidate CTE and one global order/limit, or at minimum a REPEATABLE READ transaction plus a global cap.

Q5. The CMS witnesses intentionally make claimed CMS bytes serveable where they previously false-404ed. They do not bypass tenant or actor authorization: the byte routes still require actor visibility before calling the resolver ([content route:84](<lane-worktree>/src/app/api/artifacts/[artifactId]/versions/[versionId]/content/route.ts:84)), while context candidacy still applies org, ownership, accepted-binding, and `pinnable` gates. Thus there is no new exposure to an otherwise unauthorized actor—except that the stale-winner window in Q3 can continue treating a superseded claimant as eligible.

Q6. Besides Q3 and Q4, the resolver’s witnessed branch is missing the registered-artifact-type check. It admits `object_content_snapshots OR witness` without requiring `o.type = ANY(artifactTypeIds)` ([context-resolver.ts:388](<lane-worktree>/src/lib/artifacts/context-resolver.ts:388)), while the candidate, serve, and finalizer paths do require that type. A concurrent type change—or an internal supplied pin—can therefore resolve a witnessed revision for a currently typed-DATA row that serving/finalization later rejects. Add the same pack-type predicate to the resolver’s witness arm.
